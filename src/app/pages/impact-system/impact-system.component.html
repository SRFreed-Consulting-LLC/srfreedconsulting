01

How it fits together

Four separate deployables would normally mean four copies of the same models, services and UI primitives. They don't here: the shared code lives in two versioned libraries, pulled into each application as a git submodule. A change to a domain model is made once and adopted deliberately, at a version each application chooses.

02

Three decisions worth defending

  1. Security rules were not enough

    An AI-assisted security review found clients writing financial and order data straight to Firestore. Security rules can gate who writes, but they cannot validate what is written — a client that owns a document can still write a wrong total. Those paths moved behind Cloud Functions, which became the trusted boundary where validation and authorisation actually happen.

  2. Offline-first came from the field, not the whiteboard

    The reader is used in rural Zambia, where people often have connectivity only at the moment the app is installed. That single constraint drove Firestore cache configuration, content prefetch at install time, and a reading experience that never assumes a network.

  3. Staff had to be able to ship without me

    A ministry cannot depend on one engineer to publish a lesson. The CMS and the Library Manager exist so non-technical staff create, translate and deploy content themselves — which is also what makes the system survivable if I step away.
